# 为什么数据库设计不是把字段放进表里：范式、冗余和索引怎么选择

刚开始设计数据库时，通常会先想：

- 需要几张表
- 每张表有哪些字段
- 表之间怎样关联

只要数据能够保存，接口能够查询，设计看起来就完成了。

但真实系统里的数据库还要长期面对：

- 数据不断增长
- 查询方式不断变化
- 多个请求并发修改
- 历史数据不能随意改变
- 表结构持续升级

所以数据库设计真正需要考虑的是：

> **数据之间是什么关系，哪些规则必须永远成立，以及未来准备怎样读取和修改它们。**

---

# 为什么要做范式设计

假设把订单和用户信息全部放在一张表里：

```text
order_id
user_id
user_name
user_phone
product_id
product_name
product_price
quantity
```

同一个用户下十次订单，姓名和手机号就会重复保存十次。

同一个商品卖出一万次，商品名称也会重复一万次。

这会带来几个问题：

- 浪费存储空间
- 修改用户信息时需要更新很多行
- 一部分更新成功、一部分失败时数据不一致
- 不知道哪一份才是最新数据

因此通常会把数据拆开：

```text
用户表
商品表
订单表
订单明细表
```

订单里只保存 `user_id`，商品信息通过 `product_id` 关联。

这种拆分背后的核心不是追求表越多越好。

而是：

> **同一个事实尽量只在一个地方维护。**

这就是范式设计最重要的价值。

---

# 范式不是越严格越好

如果所有数据都只保留一份，每次读取都可能需要关联很多表。

例如订单列表需要展示：

- 用户昵称
- 商品名称
- 商品图片
- 店铺名称
- 支付状态
- 物流状态

完全按照当前数据实时关联，可能需要多个 JOIN，甚至调用多个服务。

数据量变大以后，查询可能越来越复杂。

因此真实系统有时会主动保存重复数据。

这通常叫做：

> **反范式设计。**

反范式不是不懂数据库设计。

而是在明确代价以后，用数据冗余换取读取效率、历史稳定性或系统边界。

---

# 第一种冗余：保存历史快照

假设用户购买商品时，商品名称是：

> 黑色机械键盘

一个月后，商家把商品名称改成：

> 无线机械键盘

历史订单应该显示哪个名称？

通常应该显示下单时的商品信息。

因此订单明细可能保存：

- 商品 ID
- 下单时的商品名称
- 下单时的价格
- 下单时的规格

这些字段虽然和商品表重复，但它们表达的不是同一个事实。

商品表表示：

> 商品现在是什么样

订单快照表示：

> 用户下单时买的是什么

所以历史快照不能简单理解成性能优化。

它本身就是业务数据。

---

# 第二种冗余：减少高频查询成本

假设文章表里保存一个评论数量：

```text
comment_count = 128
```

这个数量也可以每次从评论表中执行 `COUNT` 得到。

但文章列表每次都统计大量评论，成本可能很高。

于是可以在文章表里冗余保存统计结果。

读取时很快。

修改时却变复杂了：

```text
创建评论
  ↓
评论数量加一
```

如果评论创建成功，数量更新失败，两份数据就会不一致。

因此做性能冗余之前必须回答：

- 原始数据在哪里
- 冗余字段怎样更新
- 更新失败怎样补偿
- 能否根据原始数据重新计算
- 允许不一致多久

如果这些问题没有答案，冗余只是在提前制造数据问题。

---

# 第三种冗余：跨服务保存必要信息

在分布式系统里，用户、订单和商品可能属于不同服务。

订单服务每次展示订单时都同步调用用户服务和商品服务，会产生：

- 更多网络调用
- 更高接口延迟
- 下游故障扩散
- 服务之间更强的运行时依赖

因此订单服务可能保存自己真正需要的一部分用户或商品信息。

这也是一种冗余。

但跨服务复制数据以后，需要明确：

- 哪个服务是数据来源
- 数据通过事件还是接口同步
- 同步失败怎样恢复
- 本地数据允许多旧

服务拆开以后，数据库 JOIN 消失了。

数据同步问题却不会消失。

它只是从数据库内部转移到了服务之间。

---

# 什么时候适合反范式

反范式通常适合这些情况：

- 查询非常高频，并且已经确认 JOIN 或计算是瓶颈
- 需要保存业务发生时的历史快照
- 数据跨服务，实时查询会产生不合理依赖
- 冗余数据可以从明确的数据源重新构建
- 业务可以接受短暂的最终一致性

不适合仅仅因为：

> 多查一张表感觉麻烦

就复制数据。

如果访问量很小，范式化设计通常更简单，也更不容易出错。

先保持事实只有一份，再根据真实查询压力选择冗余，往往更稳妥。

---

# 冗余以后必须确定数据源

假设商品名称同时存在于：

- 商品表
- 搜索索引
- Redis
- 订单快照

这些数据的用途并不相同。

必须明确谁是权威数据源。

例如：

- 商品表是当前商品信息的数据源
- 搜索索引可以从商品表重建
- Redis 只是缓存，可以丢失
- 订单快照是历史事实，不能跟随商品表修改

如果每一份数据都能反过来修改其他数据，系统很快就会失去明确方向。

所以冗余设计最重要的不是复制。

而是：

> **确定数据从哪里产生，向哪里传播，以及出错以后以谁为准。**

---

# 索引解决什么问题

数据库没有合适索引时，可能需要逐行检查整张表。

例如订单表有一千万行，查询：

```sql
SELECT * FROM orders WHERE order_no = ?;
```

如果 `order_no` 没有索引，数据库可能扫描大量数据才能找到结果。

增加索引以后，数据库可以通过索引快速定位对应记录。

索引很像书的目录。

目录占用额外页面，却可以避免每次从第一页开始寻找内容。

---

# 哪些字段通常需要索引

索引应该来自真实查询，而不是来自字段名称。

通常可以关注：

- `WHERE` 中经常用于过滤的字段
- `JOIN` 使用的关联字段
- 经常用于排序和分页的字段
- 需要数据库保证唯一性的字段

例如经常查询：

```sql
SELECT *
FROM orders
WHERE user_id = ? AND status = ?
ORDER BY created_at DESC
LIMIT 20;
```

那么可以考虑围绕：

```text
user_id, status, created_at
```

建立联合索引。

索引顺序需要匹配主要查询方式。

它不是把查询中出现的字段随便放在一起。

---

# 为什么不能每个字段都加索引

索引会加快一部分读取。

但每次写入数据时，数据库也要维护索引。

索引过多会带来：

- 插入和更新变慢
- 占用更多磁盘和内存
- 数据页分裂和维护成本增加
- 优化器需要在更多索引中选择

如果一张表有十个索引，插入一行数据就不只是写一份表数据。

还需要更新对应的索引结构。

所以索引是一种读写交换：

> **用更多存储和写入成本，换取特定查询更快。**

---

# 低区分度字段不一定适合单独建索引

假设订单状态只有：

- 待支付
- 已支付
- 已关闭

如果大部分订单都是已支付，只按 `status` 查询仍然可能命中大量行。

数据库有时会认为扫描表比使用这个索引更划算。

但这不代表状态字段永远不能进入索引。

如果查询经常是：

```text
查询某个用户的待支付订单
```

那么 `user_id + status` 的联合索引可能很有价值。

索引是否有效，取决于完整查询条件和数据分布。

不能只看某一个字段。

---

# 唯一索引不只是性能工具

普通索引主要帮助查询。

唯一索引还可以表达业务规则。

例如：

- 用户邮箱不能重复
- 一个订单只能有一条支付记录
- 同一条消息只能创建一条消费记录

即使多个请求同时查询到“不存在”，真正写入时也只能有一个成功。

所以唯一索引同时承担：

- 查询加速
- 数据约束
- 并发兜底

能够由数据库直接保证的关键不变量，不应该只依赖应用代码里的查询判断。

---

# 索引是否有效需要验证

添加索引以后，不代表数据库一定会使用。

可能出现：

- 查询条件和索引顺序不匹配
- 数据量太小，扫描全表更快
- 返回数据比例太高
- 对索引字段进行了不合适的函数计算
- 查询还需要大量回表

因此索引设计应该结合：

- 慢查询日志
- `EXPLAIN`
- 实际数据分布
- 接口延迟
- 写入成本

不要凭感觉一次创建很多索引。

也不要看到一次全表扫描就立即认为数据库设计有问题。

---

# 表结构也需要为变化留空间

数据库设计不是上线以后永远不变。

增加字段、修改索引和迁移数据时，需要考虑旧版本服务仍然可能在线。

例如直接把一个新字段设为必填，旧服务写入时可能立刻失败。

更稳妥的过程通常是：

```text
增加可空字段
  ↓
发布兼容新旧字段的代码
  ↓
逐步回填历史数据
  ↓
确认完成后再增加约束
```

表结构变化本身也是一次分布式协作。

因为发布过程中，新旧代码和新旧数据会同时存在。

---

# 在 Kratos 中怎样放置数据库设计

Kratos 的设计哲学更接近一个微服务工具箱。

它不会规定必须使用 GORM、Ent 还是 `database/sql`。

默认 Layout 更关注依赖方向：

```text
service → biz ← data
```

- `service` 负责 API DTO 和业务对象之间的转换
- `biz` 定义领域对象和 Repo 接口
- `data` 实现 Repo，并决定表结构、SQL、索引和缓存

也就是说，业务层应该表达“需要什么数据”。

数据层负责决定“怎样高效地取出来”。

---

# 订单快照应该进入 Biz 模型

订单里的商品名称和成交价格不是临时查询字段。

它们是下单时形成的历史事实。

因此可以直接出现在 `internal/biz` 的订单模型中：

```go
// internal/biz/order.go
package biz

type OrderItem struct {
	ProductID          int64
	ProductNameSnapshot string
	DealPriceCent      int64
	Quantity           int32
}

type Order struct {
	ID     int64
	UserID int64
	Items  []OrderItem
}
```

这里没有 ORM Tag，也没有 Proto 类型。

因为 `OrderItem` 表达的是业务对象，不是数据库怎样保存它。

`data` 层可以把它转换成自己的持久化模型：

```go
// internal/data/order.go
package data

type orderItemPO struct {
	ID                  int64  `db:"id"`
	OrderID             int64  `db:"order_id"`
	ProductID           int64  `db:"product_id"`
	ProductNameSnapshot string `db:"product_name_snapshot"`
	DealPriceCent       int64  `db:"deal_price_cent"`
	Quantity            int32  `db:"quantity"`
}
```

PO 跟随数据库结构变化。

DO 跟随业务含义变化。

两者分开以后，增加索引或者更换 ORM 不需要污染业务模型。

---

# Repo 接口应该表达查询意图

Kratos Layout 把 Repo 接口定义在 `biz`，由 `data` 反向实现。

例如订单业务真正需要的是：

```go
// internal/biz/order.go
package biz

import "context"

type OrderRepo interface {
	Create(context.Context, *Order) error
	FindByID(context.Context, int64) (*Order, error)
	ListByUser(context.Context, int64, ListOrderQuery) ([]*Order, error)
}

type ListOrderQuery struct {
	Status string
	Limit  int
	Cursor int64
}
```

不要为了“通用”把 SQL 细节直接暴露给 `biz`：

```go
// 不推荐：业务层开始依赖存储表达式
Find(where string, args ...any)
```

联合索引怎样设计，应该由 `data` 根据查询语义决定。

例如 `ListByUser` 最终使用：

```sql
SELECT id, user_id, status, created_at
FROM orders
WHERE user_id = ?
  AND status = ?
  AND id < ?
ORDER BY id DESC
LIMIT ?;
```

那么 `data` 层可以结合实际数据分布评估：

```text
(user_id, status, id)
```

这样的联合索引。

Repo 隔离的是存储实现。

它不应该让业务层假装数据库查询不存在成本。

---

# 小结

范式设计的核心是：

> **同一个事实尽量只维护一份。**

反范式设计则是在明确需求以后，为历史快照、读取性能或服务边界保存额外数据。

冗余之前需要确定：

- 权威数据源
- 更新方式
- 一致性要求
- 失败补偿
- 重建能力

索引也不是越多越好。

它应该从真实查询和业务约束中产生，并通过执行计划和运行数据验证。

数据库设计最终是在几个目标之间做平衡：

- 数据正确
- 查询足够快
- 写入成本可接受
- 结构能够继续演进

真正重要的不是表拆得多细，也不是索引建了多少。

而是：

> **每一份数据为什么存在、以谁为准，以及系统怎样长期保证它正确。**
