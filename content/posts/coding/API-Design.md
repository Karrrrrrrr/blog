# 为什么接口设计不只是定义请求和响应：调用方真正依赖的是语义

刚开始写接口时，通常会关注：

- 路径叫什么
- 请求有哪些字段
- 返回什么 JSON

只要前端能够调用，接口设计看起来就完成了。

但真实系统里的接口还需要回答很多问题：

- 重复调用会发生什么
- 超时以后能不能重试
- 错误是业务拒绝还是系统故障
- 批量操作只成功一部分怎么办
- 数据量变大以后怎样分页

因此接口真正提供的不是一段 JSON。

而是：

> **调用方和服务端之间的一份行为契约。**

---

# 先确定接口代表什么业务动作

假设需要做一个“取消订单”接口。

看起来只是把订单状态改成已取消。

但业务上可能还需要：

- 判断当前状态能否取消
- 释放库存
- 退回优惠券
- 关闭支付单
- 记录取消原因

所以接口不应该表达成：

```text
把 status 修改为 cancelled
```

它真正表达的是：

```text
取消订单
```

一个是修改数据库字段。

一个是执行业务行为。

接口应该围绕业务能力设计，而不是把数据库更新直接暴露出去。

---

# 查询接口和命令接口关注点不同

查询接口通常不会改变业务状态。

它关注的是：

- 查询条件
- 排序
- 分页
- 数据新鲜度

命令接口会改变业务状态。

例如：

- 创建订单
- 确认收货
- 取消支付
- 发放优惠券

它还需要考虑：

- 当前状态是否允许执行
- 重复执行是否安全
- 执行成功以后怎样查询结果
- 部分步骤失败以后怎样恢复

这两类接口不一定要使用不同技术。

但设计时应该先知道自己在处理查询还是业务命令。

---

# 接口边界不能太细

假设下单需要：

```text
创建订单
扣减库存
使用优惠券
创建支付单
```

如果把每个数据库动作都交给客户端调用：

```text
客户端先创建订单
再扣库存
再使用优惠券
再创建支付单
```

客户端就必须理解整个业务流程。

任何一步超时，客户端还要决定从哪里恢复。

这会导致：

- 业务规则泄露到多个客户端
- 不同客户端执行顺序不同
- 服务端很难统一保证一致性

更合理的接口边界通常是一个完整的业务意图：

> **提交订单。**

内部怎样拆分，由服务端负责。

---

# 接口边界也不能太大

如果一个接口同时完成很多没有强关联的事情，也会产生问题。

例如一个“保存用户所有设置”接口同时修改：

- 头像
- 密码
- 收货地址
- 通知偏好
- 隐私设置

调用方只想关闭营销通知，却必须提交全部用户资料。

这会增加：

- 字段覆盖风险
- 权限判断复杂度
- 并发修改冲突
- 接口演进成本

接口边界应该围绕一致的业务职责。

既不要小到暴露内部步骤，也不要大到包含互不相关的行为。

---

# 参数校验不只是检查格式

接口收到请求以后，通常需要两类校验。

第一类是格式校验：

- 字段是否为空
- 长度是否正确
- 数值范围是否合法
- 字符串格式是否正确

第二类是业务校验：

- 订单是否属于当前用户
- 当前状态能否退款
- 库存是否足够
- 优惠券是否可以用于这个商品

格式校验可以在接口入口完成。

业务校验应该由真正掌握业务规则的领域逻辑完成。

如果把所有规则都堆在 Handler 里，其他调用入口很容易绕过这些规则。

---

# 错误需要稳定的语义

假设接口只返回：

```json
{
  "message": "操作失败"
}
```

调用方无法知道应该：

- 提示用户修改参数
- 稍后重试
- 重新登录
- 查询当前状态
- 联系客服

接口错误通常需要区分：

- 参数错误
- 权限错误
- 资源不存在
- 业务状态冲突
- 请求过于频繁
- 下游暂时不可用
- 服务内部错误

错误码应该表示稳定的机器语义。

错误文案则用于帮助人理解，可以根据语言和产品体验调整。

调用方不应该通过匹配错误文案决定业务流程。

---

# 是否可以重试应该明确

同样是失败，处理方式可能完全不同。

例如：

```text
余额不足 → 重试不会改变结果
网络抖动 → 稍后重试可能成功
请求超时 → 上一次结果未知
```

调用方不能简单地看到错误就重试。

接口设计需要明确：

- 哪些错误可以重试
- 重试是否需要使用相同请求 ID
- 是否应该先查询业务状态
- 最大等待时间是多少

重试语义是接口契约的一部分。

不是调用方可以随意添加的实现细节。

---

# 创建接口需要考虑幂等

假设创建订单接口已经执行成功，但响应在网络中丢失。

客户端再次提交同一份请求。

服务端需要判断：

- 这是新的下单行为
- 还是上一次请求的重试

因此重要的创建接口通常需要一个稳定的业务请求 ID。

同一个 ID 重复提交时，服务端不应该创建多个业务对象。

幂等并不一定表示每次返回完全相同的 HTTP 内容。

它首先保证的是：

> **重复调用不会重复产生业务效果。**

---

# 异步接口要返回什么

有些操作无法在一次请求内完成。

例如：

- 导出大量数据
- 视频转码
- 批量生成账单
- 大规模数据同步

接口不应该让客户端一直等待几十分钟。

可以先返回一个任务 ID：

```json
{
  "task_id": "export-1001",
  "status": "pending"
}
```

调用方再通过任务 ID 查询状态。

异步接口需要提前定义：

- 有哪些状态
- 失败后是否自动重试
- 结果保留多久
- 能否取消
- 重复提交怎样处理

只返回一句“任务已提交”，但没有查询方式，调用方仍然不知道最终结果。

---

# 批量接口要面对部分成功

假设一次请求创建 100 个用户。

其中 98 个成功，2 个失败。

接口应该返回成功还是失败？

这取决于业务语义。

可能有两种设计：

- 要么全部成功，要么全部失败
- 允许部分成功，并返回每一项结果

如果允许部分成功，响应需要能够表达：

```text
第 1 项成功
第 2 项参数错误
第 3 项已经存在
```

调用方重试时，也应该只重试失败部分，或者使用稳定的项目标识保证幂等。

批量接口不是在单条接口外面简单加一个数组。

它会引入新的事务边界和错误语义。

---

# 分页需要稳定顺序

假设订单列表只按照创建时间排序。

多条订单可能拥有相同的创建时间。

翻页时，数据库可能每次返回不同顺序，导致：

- 某条数据重复出现
- 某条数据被跳过

因此分页排序通常需要一个稳定的唯一条件。

例如：

```text
created_at DESC, id DESC
```

页码分页适合数据量较小、允许跳页的场景。

游标分页更适合持续增长的数据流。

选择分页方式时，需要考虑：

- 数据是否会频繁新增或删除
- 是否需要跳到指定页
- 排序字段是否稳定
- 数据量会增长到什么程度

---

# 空值和空集合不是同一回事

接口返回：

```json
{
  "items": null
}
```

和：

```json
{
  "items": []
}
```

对调用方可能有不同含义。

`null` 可能表示没有加载、未知或不存在。

空数组通常表示已经查询，只是没有结果。

类似的区别还包括：

- 字段缺失
- 字段为空字符串
- 字段显式为 `null`
- 数值为 0

这些状态应该根据业务语义稳定使用。

不能让调用方依靠猜测理解服务端意图。

---

# 不要设计一个万能接口

有时为了减少接口数量，会设计：

```text
POST /operate
```

再通过一个 `type` 字段决定执行什么操作。

开始时可能只有两种类型。

以后不断增加：

- 创建
- 修改
- 删除
- 审核
- 取消
- 重试

最终这个接口会拥有大量互斥字段和复杂分支。

权限、校验和错误语义也混在一起。

接口数量少不代表接口设计简单。

清晰的业务边界通常比一个万能入口更容易维护。

---

# 文档和测试也是接口的一部分

如果只有服务端代码能够说明接口行为，调用方就很难正确使用。

接口文档至少应该说明：

- 字段含义和单位
- 必填与可选
- 错误码
- 幂等和重试语义
- 分页规则
- 示例

同时可以通过契约测试验证：

- 响应结构没有意外变化
- 错误语义仍然一致
- 新字段不会破坏旧调用方

接口一旦被多个系统依赖，文档和测试就是维护契约的工具。

---

# Kratos 的 API-first 思想

Kratos 倾向于先使用 Protobuf 定义接口契约，再生成 HTTP 和 gRPC 代码。

同一个业务方法只维护一份 IDL：

```proto
syntax = "proto3";

package order.v1;

import "google/api/annotations.proto";

service OrderService {
  rpc CancelOrder (CancelOrderRequest) returns (OrderReply) {
    option (google.api.http) = {
      post: "/v1/orders/{id}:cancel"
      body: "*"
    };
  }
}

message CancelOrderRequest {
  int64 id = 1;
  string request_id = 2;
  string reason = 3;
}

message OrderReply {
  int64 id = 1;
  string status = 2;
}
```

这里的重点不是 Protobuf 语法。

而是 API 契约独立存在于 `api` 目录，由生成代码统一 HTTP 和 gRPC 行为。

不要先手写一套 HTTP Handler，再单独维护另一套 gRPC 接口。

---

# Service 层应该保持薄

Kratos Layout 中的 `internal/service` 是传输适配层。

它负责：

- 接收生成的 DTO
- 完成必要的格式转换
- 调用 Biz 用例
- 返回 API DTO

例如：

```go
// internal/service/order.go
package service

func (s *OrderService) CancelOrder(
	ctx context.Context,
	req *v1.CancelOrderRequest,
) (*v1.OrderReply, error) {
	order, err := s.uc.Cancel(ctx, biz.CancelOrderCommand{
		OrderID:   req.Id,
		RequestID: req.RequestId,
		Reason:    req.Reason,
	})
	if err != nil {
		return nil, err
	}
	return &v1.OrderReply{
		Id:     order.ID,
		Status: order.Status,
	}, nil
}
```

“当前订单能不能取消”不应该写在这里。

因为同一个用例以后还可能被 MQ 消费者或定时任务调用。

Service 只负责协议边界，业务规则留在 `biz`。

---

# 使用 Kratos Error 表达稳定语义

Kratos Error 包含四类信息：

- `code`：大类语义，可以映射 HTTP 和 gRPC 状态
- `reason`：服务内稳定的错误原因
- `message`：给人阅读的提示
- `metadata`：可扩展的附加信息

Biz 可以返回明确错误：

```go
package biz

import "github.com/go-kratos/kratos/v3/errors"

func orderStateConflict(status string) error {
	return errors.Conflict(
		"ORDER_STATE_CONFLICT",
		"current order state does not allow cancellation",
	).WithMetadata(map[string]string{
		"current_status": status,
	})
}
```

调用方应该根据 `code` 和 `reason` 决定行为。

不要匹配 `message` 文案判断是否重试。

同时也不要把所有业务拒绝都包装成 500。

错误语义正确以后，Kratos 的网关、中间件、指标和 Trace 才能正确区分业务失败与系统故障。

> 以下代码示例使用 Kratos v3；v2 项目需要把导入路径中的 `/v3` 替换为 `/v2`，并根据实际版本重新生成接口代码。

# 小结

接口设计不只是定义路径和 JSON。

它需要明确：

- 这是查询还是业务命令
- 接口边界代表什么业务意图
- 重复调用是否安全
- 错误以后应该怎样处理
- 异步任务怎样查询结果
- 批量操作怎样表达部分成功
- 分页顺序怎样保持稳定

好的接口会隐藏内部实现细节。

同时把调用方真正需要依赖的行为说清楚。

实现代码以后可以重构。

但接口语义一旦被使用，就会成为多个系统共同依赖的契约。

所以设计接口时，最重要的问题不是：

> **这次请求应该返回哪些字段？**

而是：

> **无论成功、失败、超时还是重复调用，双方是否都知道接下来应该做什么？**
