# 为什么数据库连接池不是越大越好：从吞吐量到并发正确性

刚开始写后端服务时，很容易有一个直觉：

> **连接越多，同时处理的请求就越多。**

如果接口变慢了，一个自然的想法就是：

- 增加服务实例
- 增加工作线程
- 调大数据库连接池

看起来只要并发足够高，系统就能处理更多请求。

但真实系统里，数据库连接池并不是越大越好。

因为连接池解决的不是：

> **怎样让所有请求立刻进入数据库。**

而是：

> **怎样限制同时进入数据库的请求数量。**

---

# 一次数据库请求经过了什么

假设一个订单接口需要查询数据库。

程序通常会做几件事：

- 从连接池获取一个连接
- 发送 SQL
- 等待数据库执行
- 读取结果
- 把连接归还连接池

连接池里的连接是可以重复使用的。

这样程序就不用每次请求都重新建立 TCP 连接、认证和初始化会话。

所以连接池首先解决的是：

> **复用数据库连接。**

但它还有另一个经常被忽略的作用：

> **控制数据库并发。**

---

# 数据库的处理能力是有限的

数据库不是一个无限扩容的黑盒。

一条 SQL 进入数据库以后，可能需要消耗：

- CPU
- 内存
- 磁盘 IO
- Buffer Pool
- 锁
- 临时表

假设数据库比较稳定时，每秒可以处理 1000 个请求。

这时即使应用同时送进去 10000 个请求，数据库也不会突然拥有十倍的处理能力。

多出来的请求只会在数据库内部等待。

于是可能出现：

- SQL 执行时间变长
- 锁等待增加
- 内存占用上升
- 数据库缓存命中率下降
- 接口开始超时

也就是说：

> **增加并发不会自动增加吞吐量。**

超过数据库的处理能力以后，增加的通常只是等待时间。

---

# 连接池太大，只是把队列推给数据库

假设服务有 1000 个请求同时到达。

如果连接池只有 50 个连接：

- 50 个请求进入数据库
- 其他请求在应用里等待连接

如果把连接池调到 1000：

- 1000 个请求一起进入数据库
- 请求改成在数据库内部等待 CPU、IO 和锁

请求并没有消失。

只是等待的位置发生了变化。

在应用里等待连接，通常还比较容易控制：

- 可以设置获取连接的超时时间
- 可以快速失败
- 可以进行限流
- 可以观察连接池状态

但大量请求一起压进数据库以后，整个数据库都可能变慢。

并且受到影响的不只是当前接口。

其他共用数据库的服务也会一起变慢。

所以连接池很像一道闸门：

> **它保护的不只是应用，也是在保护数据库。**

---

# 服务实例越多，问题越容易被放大

连接池大小不能只看单个服务实例。

例如：

- 每个实例有 100 个连接
- 一共有 20 个实例

那么数据库最多可能同时面对：

> 2000 个连接

如果扩容到 50 个实例，就可能变成 5000 个连接。

因此扩容应用时，数据库连接数也在一起增长。

如果只调整单个实例的配置，很容易忽略整个集群的总连接数。

真实系统里更应该关注：

- 所有实例的连接池总和
- 数据库允许的最大连接数
- SQL 的平均执行时间
- 高峰期活跃连接数
- 等待连接的请求数量

---

# 连接池太小也不行

连接池不是越小越好。

如果数据库还有处理能力，但应用只有很少的连接，就可能出现：

- 大量请求等待连接
- 数据库 CPU 很空闲
- 接口吞吐量上不去

所以连接池大小不是一个固定答案。

它需要根据真实运行情况调整。

通常可以观察：

- 获取连接需要等待多久
- 连接池是否长期占满
- 数据库 CPU 和 IO 是否已经饱和
- SQL 是否存在慢查询
- 锁等待是否明显增加

如果连接池一直满，但数据库很空闲，可以考虑增加连接。

如果数据库已经很忙，再增加连接通常只会让情况更差。

---

# 并发不只影响性能，也影响正确性

连接池控制的是同时进入数据库的请求数量。

但只要系统允许并发，就还要面对另一个问题：

> **多个请求可能同时修改同一份数据。**

例如系统规定：

> 一个订单只能创建一条支付记录。

程序可能先查询：

```text
订单 1001 是否已经有支付记录？
```

如果没有，就创建一条。

单个请求执行时没有问题。

但两个请求同时执行时，可能发生：

```text
请求 A 查询：不存在
请求 B 查询：不存在
请求 A 创建
请求 B 创建
```

最后同一个订单出现了两条支付记录。

这说明：

> **先查询再创建，本身不能作为最终的并发保障。**

---

# 为什么唯一索引可以兜底

如果业务规定：

> 一个订单只能有一条支付记录

那么可以在数据库里对 `order_id` 建立唯一索引。

这样两个请求同时创建时：

- 第一个请求创建成功
- 第二个请求触发唯一键冲突

应用里的两个请求虽然并发执行，但数据库会在写入时维护索引的一致性。

最终不可能同时留下两个相同的唯一键。

唯一索引把业务规则变成了数据库约束：

> **无论应用里有多少个并发请求，数据库里最终只能存在一个。**

这比只在代码里写一个 `if` 更可靠。

因为代码里的查询和创建之间存在时间窗口。

数据库约束则发生在真正写入数据的位置。

---

# 有唯一索引，为什么还要先查询

既然唯一索引可以兜底，能不能每次都直接创建？

在一些系统里可以。

但如果 Repo 的创建接口只返回成功或错误，重复创建就会产生唯一键错误。

错误随后可能经过：

- 错误包装
- Trace Span 标记
- 指标统计
- 告警系统

即使上层最后把它当作“已经处理”返回，整条 Trace 里仍然可能留下异常节点。

而消息重试、客户端重试带来的重复请求，本来就是系统预期内的情况。

因此可以先查询一次：

```text
查询到已存在 → 正常返回
查询不到     → 尝试创建
创建冲突     → 说明查询和创建之间真的发生了并发
```

这样做的目的不是替代唯一索引。

而是：

> **让普通重复请求走正常路径，把唯一约束留给真正的并发竞争。**

先查询负责减少预期错误对 Trace 的干扰。

唯一索引负责最终正确性。

两者解决的不是同一个问题。

---

# 连接池和唯一索引其实在解决同一类问题

连接池关注的是：

> 同时允许多少请求进入数据库。

唯一索引关注的是：

> 多个请求同时写入时，哪些结果可以被接受。

一个保护数据库容量。

一个保护业务数据。

它们背后的共同思路是：

> **不要假设并发越多越好，也不要假设请求会按顺序执行。**

---

# 小结

数据库连接池不是越大越好。

连接太少，可能浪费数据库能力。

连接太多，则可能把大量等待和竞争压进数据库，让整个系统一起变慢。

连接池需要根据：

- 数据库容量
- SQL 执行时间
- 服务实例数量
- 真实流量

进行调整。

与此同时，只要系统存在并发，业务正确性就不能只依赖应用里的查询判断。

先查询可以过滤普通重复请求，让 Trace 更干净。

唯一索引则在真正发生并发时保证：

> **数据库里最终只能留下符合业务规则的数据。**

真实系统关注的不只是能同时处理多少请求。

还要关注：

> **这些请求同时到达以后，系统是否仍然稳定，数据是否仍然正确。**
