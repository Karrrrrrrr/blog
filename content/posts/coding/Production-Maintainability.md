# 为什么系统上线以后更关注日志和接口：代码之外的长期维护

开发一个新功能时，注意力通常都在代码上。

例如：

- 业务逻辑怎么实现
- 数据库怎么设计
- 接口能不能正常返回

功能测试通过以后，代码看起来就完成了。

但系统上线以后，真正困难的问题往往变成：

> **用户说出问题了，我们怎么知道发生了什么？**

以及：

> **半年以后需求变化，原来的接口还能不能继续使用？**

这时影响维护成本的，已经不只是代码写得好不好。

还包括：

- 系统有没有留下足够的运行现场
- 对外接口有没有给未来变化留下空间

---

# 代码只能说明应该发生什么

假设用户反馈：

> 订单支付成功了，但状态一直没有更新

开发人员打开代码，看到流程是：

```text
1. 接收支付回调
2. 查询订单
3. 更新订单状态
4. 发送通知
```

代码逻辑没有明显问题。

但线上那一次请求到底发生了什么，代码无法回答。

可能是：

- 回调根本没有到达
- 签名校验失败
- 没有查询到订单
- 数据库更新超时
- 事务提交成功但响应失败
- 消息发送失败后等待补偿

代码展示的是可能路径。

日志和 Trace 记录的才是实际走过的路径。

所以在排查线上问题时：

> **代码告诉我们系统应该怎样运行，运行记录告诉我们它当时究竟怎样运行。**

---

# 为什么只打印一句失败没有帮助

很多程序会记录：

```text
处理失败
```

这句话几乎没有排查价值。

真正有用的信息通常包括：

- 哪个请求失败
- 哪个用户或订单受到影响
- 执行到了哪一步
- 调用了哪个下游
- 使用了什么关键参数
- 错误类型是什么
- 是否会自动重试

例如：

```text
order_id=1001
request_id=pay-1001
action=update_order_status
result=failed
reason=db_timeout
```

有了这些上下文，才能把一条错误和真实业务关联起来。

---

# 日志、指标和 Trace 解决不同问题

线上可观测性通常不只有日志。

指标适合回答：

- 错误率是否突然升高
- 接口延迟是否变慢
- 当前有多少请求
- 数据库连接池是否占满

日志适合回答：

- 某一步具体发生了什么
- 某个业务 ID 为什么失败
- 程序记录了哪些上下文

Trace 适合回答：

- 一次请求经过了哪些服务
- 时间花在了哪里
- 哪个 Span 出现异常
- 上下游调用关系是什么

它们不是互相替代的关系。

更像是：

```text
指标发现问题
   ↓
Trace 定位问题发生在哪一段
   ↓
日志查看具体业务上下文
```

---

# 预期内的错误也会污染 Trace

假设系统为了处理幂等，直接尝试创建一条已经存在的数据。

数据库返回唯一键冲突。

业务层可能知道：

> 这只是重复请求，可以当作成功

但错误从 Repo 返回以后，可能已经经过：

- 错误包装
- Span Error 标记
- 错误指标统计
- Trace 上报

即使最外层接口最终返回成功，链路中间仍然留下了异常节点。

以 Kratos v3 的默认 Middleware 为例，只要 Handler 最终返回的 `error` 不是 `nil`：

- Logging Middleware 会按 Error 级别记录请求
- Tracing Middleware 会调用 `RecordError`
- Server Span 会被标记为 Error

Kratos Error 的 Code 和 Reason 可以保留业务语义，但 `Conflict`、`BadRequest` 仍然是非 `nil` Error，不会自动变成成功 Span。

如果 Biz 已经识别并处理了某个分支，最终返回 `nil`，Server Middleware 不会再把请求标记为失败。

但这不代表整条链路一定干净。

数据库或 RPC Client 的子 Span 可能已经在唯一键冲突发生时记录 Error，上层不能撤销已经完成的子 Span。

如果大量正常重试都走这条路径，真正的错误会被淹没。

因此可观测性也会影响代码流程设计。

例如幂等创建时，可以先查询：

```text
已经存在 → 正常返回
不存在   → 尝试创建
```

唯一约束仍然负责并发兜底。

先查询则让普通重复请求不产生预期错误，保持 Trace 干净。

真正并发竞争产生的唯一键冲突仍然保留为异常信号，因为它确实表示查询和创建之间发生了状态变化。

---

# 日志不是越多越好

为了方便排查，也不能把所有内容都打印出来。

日志太多会带来：

- 存储成本
- 查询噪声
- 性能开销
- 敏感信息泄露风险

密码、Token、身份证号和完整支付信息不应该直接进入日志。

循环中的大量重复日志也可能让真正重要的信息难以找到。

日志设计需要回答：

- 这条信息以后能帮助定位什么问题
- 是否已经有指标或 Trace 记录
- 是否包含敏感数据
- 是否需要采样
- 日志级别是否正确

有用的运行记录不是把程序每一步都打印出来。

而是在关键状态变化处留下足够上下文。

---

# 为什么接口比实现活得更久

代码实现可以随时重构。

只要行为不变，调用方通常不会知道内部发生了变化。

但接口一旦被其他系统使用，就形成了契约。

调用方可能包括：

- Web 前端
- App
- 其他服务
- 第三方合作方
- 已经无法及时升级的旧客户端

这时修改一个字段，影响的不再是一个仓库里的代码。

而是所有调用方。

因此接口设计需要考虑的不只是当前需求能不能完成。

还要考虑：

> **需求变化以后，旧调用方还能不能继续工作。**

---

# 一个看起来简单的字段变化

假设订单接口最初返回：

```json
{
  "paid": true
}
```

当时订单只有已支付和未支付两种状态。

后来业务增加：

- 支付中
- 支付失败
- 已退款
- 部分退款

一个布尔值已经无法表达这些状态。

如果一开始返回的是：

```json
{
  "payment_status": "paid"
}
```

以后可以增加新的状态值。

但调用方仍然需要能够处理未知状态。

否则服务端一增加枚举值，旧客户端就可能崩溃。

接口设计不仅要给服务端留下扩展空间。

调用方也要对未来出现的新值保持容忍。

---

# 字段只能增加，不能删除吗

兼容接口时，增加可选字段通常比修改已有字段更安全。

例如原接口返回：

```json
{
  "name": "商品 A"
}
```

增加一个可选字段：

```json
{
  "name": "商品 A",
  "subtitle": "限时优惠"
}
```

旧客户端通常会忽略不认识的字段。

但下面这些修改可能破坏兼容性：

- 删除字段
- 修改字段类型
- 改变字段含义
- 把可选字段改成必填
- 改变错误码语义

因此字段名一旦公开，真正稳定的应该是它的语义，而不只是 JSON 格式。

---

# 不要把数据库结构直接当成接口

为了开发方便，有时会把数据库模型直接返回给调用方。

这样开始时写得很快。

但数据库字段一旦变更，接口也会跟着变化。

还可能意外暴露：

- 内部状态
- 删除标记
- 审计字段
- 不应该公开的数据

数据库模型解决的是内部存储问题。

接口模型解决的是外部契约问题。

它们变化的原因和速度并不相同。

分开以后，内部可以重构存储结构，而不必强迫所有调用方一起修改。

---

# 创建接口也要考虑重复调用

接口设计不仅是字段设计。

还包括调用语义。

例如创建订单接口超时以后，客户端可能重新请求。

如果接口没有稳定的业务请求 ID，就无法判断：

- 这是一个新订单
- 还是上一次请求的重试

因此重要的创建接口通常需要提前考虑：

- 幂等标识
- 重复请求的返回方式
- 状态查询接口
- 超时后的恢复流程

这些能力在接口第一次上线时可能用不到。

但真正发生网络超时以后再补，调用方往往已经很多了。

---

# 分页接口也会遇到未来变化

数据量很小时，接口可以一次返回全部记录。

以后数据变多，再增加分页，就会改变响应结构和调用方式。

如果一开始就确定数据会持续增长，可以提前设计分页。

但这不代表所有接口都要过度设计。

真正需要判断的是：

- 数据是否天然会增长
- 调用方是否需要稳定排序
- 翻页过程中数据是否会变化
- 使用页码还是游标

接口为未来变化留空间，不等于猜出未来所有需求。

而是避免把当前偶然条件写成永远不能改变的契约。

---

# 版本号不是第一选择

接口不兼容时，可以发布新的版本。

例如：

```text
/api/v1/orders
/api/v2/orders
```

但版本号也会带来维护成本：

- 多套实现同时存在
- Bug 修复需要同步
- 旧版本长期无法下线
- 文档和测试越来越多

所以更好的方式通常是：

> **优先进行兼容性扩展，真正无法兼容时再增加版本。**

版本号可以解决破坏性变化。

但不能代替一开始对接口语义的认真设计。

---

# 日志和接口为什么可以放在一起讨论

接口决定系统怎样被使用。

日志、指标和 Trace 决定系统被使用以后，我们能看见什么。

如果接口没有业务请求 ID：

- 重试难以识别
- 日志难以关联
- Trace 难以对应到业务操作

如果错误码没有稳定语义：

- 调用方不知道是否应该重试
- 监控无法正确分类错误
- 告警中混合了业务失败和系统故障

好的接口契约会让可观测性更清楚。

好的可观测性也会暴露接口设计中的问题。

---

# 小结

系统上线以前，代码是主要工作对象。

系统上线以后，维护人员面对的是：

- 用户反馈
- 请求链路
- 历史数据
- 旧客户端
- 不断变化的业务需求

这时日志、指标和 Trace 决定问题能不能被找到。

接口契约决定系统能不能继续演进。

运行记录需要说明：

- 哪个业务受到影响
- 请求经过了哪些服务
- 哪一步发生了什么
- 系统接下来是否会恢复

接口设计则需要考虑：

- 字段语义能否扩展
- 旧调用方能否兼容
- 重复调用是否安全
- 数据增长以后是否仍然适用

所以真实系统里，日志有时会比眼前的代码更重要。

不是因为代码不重要。

而是因为线上故障发生以后：

> **代码仍然在那里，真正缺少的是当时发生了什么。**

接口也是一样。

真正困难的不是今天把它设计出来。

而是几年以后，它仍然能够被旧系统使用，也能容纳新的业务变化。
