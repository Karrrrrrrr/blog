# DDD 到底在解决什么问题：不是换一套目录名称

第一次接触 DDD 时，经常会看到很多新名词：

- 实体
- 值对象
- 聚合
- 领域服务
- 仓储
- 领域事件

于是很容易认为，DDD 就是把原来的代码重新放进几个目录：

```text
domain
application
infrastructure
```

目录调整以后，项目看起来很专业。

业务代码却可能和以前完全一样。

DDD 真正想解决的不是代码放在哪里。

而是：

> **业务变复杂以后，怎样让代码仍然能够准确表达并保护业务规则。**

---

# 简单 CRUD 为什么会逐渐失控

假设最开始只有一个订单表。

接口需要：

- 创建订单
- 查询订单
- 修改状态

使用 Handler、Service、Repo 三层，很快就能完成。

后来业务增加：

- 不同商品有不同取消规则
- 支付后不能直接改价
- 发货后退款需要走售后
- 会员和普通用户优惠不同
- 某些订单需要人工审核

这些规则可能逐渐散落在：

- Handler 的参数判断
- Service 的多个 `if`
- Repo 的更新条件
- 定时任务
- MQ 消费者

最后任何地方都可以直接修改订单状态。

开发人员很难回答：

> 一个订单到底允许怎样变化？

DDD 首先关注的就是把这些业务规则重新放回业务模型。

---

# 领域不是数据库表

数据库表描述数据怎样保存。

领域模型描述业务怎样运行。

例如订单表可能只有：

```text
id
status
amount
```

但业务中的订单还拥有行为：

- 支付
- 取消
- 发货
- 确认收货
- 申请退款

如果代码只有一组字段和通用的 `UpdateStatus`，任何调用方都可能把订单从任意状态改成任意状态。

更接近业务的模型可能提供：

```text
order.Pay()
order.Cancel()
order.Ship()
```

每个行为内部检查自己的业务条件。

这样代码表达的不再是修改一个字段。

而是在执行一个业务动作。

---

# 统一语言为什么重要

同一个词在不同人眼里可能有不同含义。

例如“用户”可能表示：

- 登录账号
- 下单顾客
- 收货人
- 商家员工
- 系统操作员

如果产品、开发和数据库都使用同一个 `user` 表达所有概念，讨论很容易混乱。

DDD 强调统一语言。

也就是产品、开发和代码尽量使用一致的业务词汇。

例如明确区分：

- Account：登录账号
- Customer：购买者
- Recipient：收货人
- Operator：后台操作员

统一语言的价值不是英文命名更漂亮。

而是：

> **当代码写着“取消订单”时，它和业务人员说的“取消订单”表达同一个规则。**

---

# 限界上下文：同一个词不必全系统相同

统一语言不代表整个公司只能有一套模型。

例如“商品”在不同业务里关注点不同。

商品中心关心：

- 标题
- 类目
- 规格
- 上下架

库存系统关心：

- SKU
- 仓库
- 可用数量
- 锁定数量

订单系统关心：

- 下单时名称
- 成交价格
- 购买数量

它们都叫商品，却不是同一个模型。

DDD 使用限界上下文划分语义边界。

在一个上下文内，模型和词义保持一致。

跨上下文时，通过明确接口或事件传递需要的信息。

这样订单系统不需要依赖商品中心内部的完整模型。

---

# 实体关注身份和生命周期

实体最重要的特点是拥有稳定身份。

例如订单即使发生变化：

- 状态改变
- 地址修改
- 金额调整

它仍然是同一个订单。

订单 ID 用来识别它的身份。

判断两个实体是不是同一个，通常看身份，而不是所有字段是否相等。

实体还会经历自己的生命周期。

例如：

```text
待支付 → 已支付 → 已发货 → 已完成
```

实体应该保护生命周期中的业务规则。

---

# 值对象关注值本身

有些概念不需要独立身份。

例如金额可以由下面两部分组成：

```text
数值 + 币种
```

`100 CNY` 和另一个 `100 CNY` 在业务上可以认为相等。

它们不需要各自拥有 ID。

这类概念适合建模为值对象。

值对象可以集中保护规则：

- 金额不能随意和不同币种相加
- 地址必须包含必要字段
- 时间范围的开始不能晚于结束

如果这些概念始终以一组松散字段传递，校验逻辑就会在项目里重复出现。

---

# 聚合保护业务不变量

聚合是 DDD 中容易被误解的概念。

可以先把它理解成：

> **需要在一次业务操作中共同保持正确的一组对象。**

例如订单包含多个订单项。

业务规定：

- 订单总金额等于订单项金额之和
- 已取消订单不能新增订单项
- 订单项不能脱离订单单独存在

那么订单可以作为聚合根，统一控制订单项的修改。

外部不能绕过订单直接改变内部对象。

这些始终必须成立的规则，通常叫做不变量。

聚合的核心职责就是：

> **在每次状态变化以后，仍然保证不变量成立。**

---

# 聚合边界通常也是事务边界

一个聚合内的修改，通常希望在一个本地事务里完成。

如果一次操作需要同时修改很多巨大对象，聚合就会变得很重。

可能出现：

- 锁范围变大
- 并发冲突增加
- 每次加载大量数据
- 一个事务持续很久

所以聚合不是越大越完整。

应该只把必须强一致的数据放在一起。

聚合之间的协作通常通过：

- 应用服务编排
- 领域事件
- 最终一致性

完成。

聚合边界同时表达了一个重要选择：

> **哪些规则必须立刻一致，哪些规则可以稍后完成。**

---

# 应用服务负责流程，领域对象负责规则

假设需要取消订单。

应用服务可以负责：

```text
加载订单
  ↓
调用 order.Cancel()
  ↓
保存订单
  ↓
发布订单已取消事件
```

“已发货订单不能取消”这个规则应该由订单保护。

而不是只写在某个 HTTP Handler 里。

因为取消操作以后还可能来自：

- 后台管理系统
- 定时任务
- MQ 消费者

应用服务负责组织一次用例。

领域对象负责保证业务规则。

这样不同入口执行同一个行为时，不会各自复制一套判断。

---

# 领域服务什么时候使用

有些业务规则不自然属于某一个实体。

例如：

- 根据买家、卖家和商品计算交易费用
- 比较两个账户之间是否允许转账
- 根据多种策略选择仓库

这时可以使用领域服务表达这项规则。

但领域服务不应该变成原来那个包含所有代码的巨大 Service。

如果一个行为明显属于订单，就应该放回订单。

领域服务适合表达跨多个领域对象、但仍然属于业务规则的能力。

---

# 仓储不是简单包装数据库 CRUD

仓储为领域层提供获取和保存聚合的方式。

它的接口应该尽量使用领域语言。

例如：

```text
FindOrderByID
SaveOrder
```

而不是把数据库所有能力原样暴露：

```text
UpdateAnyField
DeleteByCondition
ExecuteSQL
```

如果领域层可以随意更新任意字段，聚合保护的业务规则就很容易被绕过。

仓储背后可以使用：

- 关系数据库
- 文档数据库
- 远程服务

领域逻辑不需要知道具体存储细节。

---

# 领域事件表达已经发生的事实

订单支付成功以后，系统可能需要：

- 扣减库存
- 增加积分
- 发送通知
- 更新统计

如果订单逻辑直接调用所有下游，订单模块会依赖越来越多系统。

可以发布一个领域事件：

> 订单 1001 已支付

其他模块根据自己的职责处理这个事实。

领域事件应该使用过去式。

因为它表示已经发生、不能假装没有发生的业务事实。

事件可以降低模块之间的直接依赖。

但也会引入：

- 异步处理
- 重复消费
- 最终一致性
- 顺序问题

所以事件不是为了让架构看起来更高级。

只有真正需要解耦和异步协作时才值得引入。

---

# 防腐层保护自己的模型

假设订单系统需要调用第三方物流接口。

第三方可能使用：

- 不同字段名称
- 不同状态定义
- 特殊错误码
- 经常变化的数据格式

如果第三方模型直接进入领域代码，整个系统都会被外部概念影响。

可以在边界处增加转换层：

```text
第三方物流模型
      ↓
转换和适配
      ↓
本系统的物流模型
```

DDD 把这类边界叫做防腐层。

它不是为了多写一层代码。

而是防止外部系统的模型污染自己的业务语言。

---

# DDD 不适合所有项目

如果系统只是：

- 简单后台管理
- 数据录入和查询
- 业务规则很少
- 生命周期很短

完整引入大量 DDD 模式可能只会增加理解成本。

DDD 更适合：

- 业务规则复杂
- 状态变化很多
- 多个团队对概念理解容易不一致
- 系统需要长期演进

即使不采用完整架构，也可以使用其中的思想：

- 使用准确的业务语言
- 让对象保护自己的规则
- 明确事务边界
- 区分业务模型和存储模型

---

# 小结

DDD 不是一套固定目录。

也不是把 Model 改名成 Entity，把 Service 改名成 Domain Service。

它更关注：

- 业务语言是否准确
- 模型边界是否清楚
- 不变量由谁保护
- 强一致范围应该多大
- 外部系统怎样进入自己的模型

实体和值对象帮助表达业务概念。

聚合保护一次事务内必须成立的规则。

应用服务组织流程，领域对象执行规则。

领域事件连接需要最终一致的不同边界。

真正判断 DDD 是否落地，不是看项目里有没有 `domain` 目录。

而是看：

> **当业务人员描述一条规则时，开发人员能不能在代码里找到唯一、清晰并且不会被绕过的表达。**
