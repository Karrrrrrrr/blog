# 为什么分布式系统里时间不可信：服务器上的现在并不相同

在单机程序里，时间看起来很可靠。

程序可以记录：

- 创建时间
- 更新时间
- 任务开始时间
- 请求耗时

还可以直接比较两个时间：

```text
时间 A 比时间 B 小
```

于是很容易认为：

> 事件 A 一定发生在事件 B 之前。

但系统分布到多台机器以后，这个结论不一定成立。

因为每台机器都有自己的时钟。

而这些时钟不可能永远完全一致。

---

# 两台服务器的现在可能不同

假设订单服务在服务器 A 上。

库存服务在服务器 B 上。

真实执行顺序是：

```text
1. 订单服务创建订单
2. 库存服务扣减库存
```

但服务器 A 的时间慢了 2 秒，服务器 B 的时间快了 2 秒。

记录出来可能变成：

```text
创建订单：10:00:02
扣减库存：10:00:06
```

看起来没有问题。

如果偏差方向相反，也可能变成：

```text
创建订单：10:00:06
扣减库存：10:00:02
```

从日志看，库存好像在订单创建之前就被扣了。

业务顺序没有错。

错的是用不同机器的本地时间推断全局顺序。

---

# 有时间同步也不能完全相同吗

服务器通常会通过 NTP 等方式校准时间。

它可以让时钟尽量接近真实时间。

但同步过程仍然受到：

- 网络延迟
- 系统负载
- 虚拟化环境
- 时钟硬件误差
- 校准间隔

影响。

所以时间同步能减少偏差，却不能保证所有机器在每一瞬间完全一致。

分布式系统通常应该接受一个事实：

> **机器之间存在时钟偏差。**

---

# 时钟还可能向前或向后调整

系统时间不仅会走得快或慢。

在校准时，它还可能发生调整。

例如程序记录任务开始时间：

```text
10:00:05
```

任务执行过程中，系统时钟向后调整了 3 秒。

结束时间可能变成：

```text
10:00:04
```

用结束时间减开始时间，得到的耗时甚至可能是负数。

因此测量一段代码执行了多久，不应该依赖可能被校准的墙上时间。

程序通常应该使用单调时钟计算时间间隔。

简单理解：

- 墙上时间回答“现在几点”
- 单调时间回答“过去了多久”

这两个问题看起来相似，实际上用途不同。

---

# 时间戳不能直接代表业务顺序

假设两个用户同时修改同一份资料。

系统准备使用 `updated_at` 判断哪次修改更新。

请求 A 在服务器 A 上执行。

请求 B 在服务器 B 上执行。

如果两个服务器时间存在偏差，较晚提交的请求可能拥有更小的时间戳。

这时使用：

> 时间戳更大的数据覆盖时间戳更小的数据

就可能保留错误版本。

对于需要严格顺序的操作，更可靠的依据通常是：

- 数据库版本号
- 自增序列
- 消息队列中的有序 Offset
- 在同一数据源内生成的提交顺序

时间戳适合帮助人理解发生时间。

但它不一定适合作为并发控制的唯一依据。

---

# 分布式锁为什么也会受到时间影响

很多分布式锁都有过期时间。

例如：

```text
服务 A 获得锁，有效期 10 秒
```

服务 A 开始处理任务后，可能因为：

- Full GC
- CPU 长时间被抢占
- 网络暂停
- 进程卡顿

停顿了十几秒。

锁已经过期，服务 B 又获得了同一把锁。

但服务 A 恢复以后，并不知道自己的锁已经失效，仍然继续写数据。

于是两个服务都认为自己拥有执行权。

所以仅仅依赖“锁还没有到期”并不足以保证正确性。

重要写操作还可以使用递增的 Fencing Token：

```text
服务 A 获得 Token 10
服务 B 后来获得 Token 11
```

数据存储只接受比当前 Token 更新的写入。

这样即使服务 A 恢复，它携带的旧 Token 也会被拒绝。

真正保护数据的是顺序编号，而不是某台机器对当前时间的判断。

---

# 过期判断应该由谁负责

假设数据库里有一个优惠券过期时间。

多个服务分别判断：

```text
当前时间是否超过 expire_at
```

如果机器时间存在偏差，它们可能在边界时刻得到不同结果。

于是同一张优惠券可能出现：

- 订单服务认为可以使用
- 优惠券服务认为已经过期

对于重要的时间规则，应该尽量明确权威来源。

例如：

- 由优惠券服务统一判断
- 由数据库条件更新进行最终校验
- 在允许范围内明确时钟偏差

不要让多个服务各自用本机时间独立决定同一个关键状态。

---

# 定时任务也不能假设只执行一次

定时任务经常按照时间触发。

例如每天零点结算订单。

在分布式部署下，可能有多个实例同时发现：

> 现在到零点了

于是同一个任务被执行多次。

服务重启、任务补偿和调度器故障，也可能让某个时间段被重复执行或暂时跳过。

所以定时任务仍然需要：

- 幂等
- 唯一任务标识
- 执行状态
- 补偿机制

时间只能说明任务大概应该什么时候开始。

不能自动保证它只执行一次。

---

# 日志时间为什么会让排查变得困难

一次请求可能经过多个服务。

如果只按照日志时间排序，可能看到：

```text
库存服务完成
订单服务开始
网关收到请求
```

这不一定是程序真的倒序执行。

也可能只是服务器时钟不一致。

因此排查分布式调用时，除了时间戳，还需要：

- Trace ID
- Span 的父子关系
- 请求 ID
- 消息 ID
- 业务 ID

调用关系比不同机器上的绝对时间更能说明事件之间的因果关系。

---

# 时间仍然有用

时间不可信，不代表时间完全不能使用。

它仍然适合：

- 展示给用户
- 按大致时间查询日志
- 设置缓存过期
- 统计业务趋势
- 记录审计信息

只是使用时间时，需要知道它能保证什么，不能保证什么。

例如：

- 可以接受几秒偏差吗
- 是否需要严格排序
- 是否跨多台机器比较
- 时钟回拨会不会影响逻辑
- 判断失败后能否重试或补偿

---

# 小结

分布式系统里的时间不可信，主要不是因为服务器没有时间同步。

而是因为：

- 每台机器都有独立时钟
- 时钟之间始终可能存在偏差
- 系统时间可能被向前或向后校准
- 时间戳不能天然代表全局执行顺序

因此：

- 计算耗时使用单调时间
- 严格排序使用版本号或序列
- 并发更新不要只比较本地时间戳
- 重要过期规则应该有明确的权威判断方
- 分布式链路使用 Trace 关系还原因果顺序

单机程序里，我们经常问：

> **现在几点？**

分布式系统里，更重要的问题是：

> **谁先发生，谁依赖谁，以及这个顺序由什么来保证？**
