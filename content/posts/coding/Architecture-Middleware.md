# 为什么架构设计不是多分几层：从依赖方向到中间件设计

提到架构设计时，经常会想到：

- 分层架构
- 微服务
- 事件驱动
- DDD
- 中间件

于是一个项目可能很快出现很多目录和模块。

但目录越多，不代表架构越好。

架构真正解决的是：

> **系统发生变化时，影响范围能不能被控制。**

如果修改一个业务规则需要同时修改接口、数据库、MQ 和多个公共组件，说明依赖边界并不清楚。

---

# 分层的目的是什么

一个常见服务可能分成：

```text
接口层
应用层
领域层
基础设施层
```

这些层不是为了让调用链更长。

而是分开不同变化原因。

例如：

- HTTP 参数格式变化，不应该影响业务规则
- 数据库从 MySQL 切换存储方式，不应该重写所有业务流程
- 业务规则变化，不应该要求修改 Trace 中间件

好的边界让不同类型的变化停留在自己的范围内。

---

# 依赖方向比目录位置更重要

即使代码放在不同目录，也可能互相随意引用。

例如领域层直接依赖：

- HTTP Request
- ORM Model
- Redis Client
- MQ SDK

这意味着业务规则已经和具体技术绑定。

技术组件一变化，领域代码就要一起变化。

更稳定的方向通常是：

```text
外部接口和基础设施
        ↓
应用用例和业务规则
```

业务层定义自己需要的能力。

基础设施层实现这些能力。

这样核心业务不需要知道请求来自 HTTP、定时任务还是消息队列。

---

# 不要为了抽象而抽象

抽象的价值是隔离真实变化。

如果一个组件只有一种实现，也没有变化可能，却提前创建很多接口、工厂和适配器，代码会更难理解。

判断是否需要抽象，可以先问：

- 这里是否有多个调用方
- 变化频率是否不同
- 是否需要隔离外部依赖
- 是否已经出现重复逻辑
- 测试是否需要替换实现

抽象应该来自已经存在的边界和变化。

不是来自对未来所有可能性的猜测。

---

# 单体不等于没有架构

很多系统一开始并不需要微服务。

一个模块清晰的单体应用，同样可以拥有良好架构。

例如在同一个进程里划分：

- 订单模块
- 库存模块
- 支付模块

模块之间通过清晰接口协作。

以后真的需要独立扩容或独立发布时，再拆成服务。

如果单体内部边界混乱，拆成微服务以后，只会把函数调用变成网络调用。

原来的耦合仍然存在，还增加了超时、重试和一致性问题。

---

# 中间件在解决什么问题

一次请求进入服务以后，很多逻辑和具体业务无关。

例如：

- 记录 Trace
- 身份认证
- 权限检查
- 限流
- 超时控制
- 异常恢复
- 指标统计

如果每个接口都重复编写这些逻辑，很容易出现不一致。

中间件允许把这些横切能力放在统一位置。

请求先经过一组中间件，再进入业务处理器。

响应则沿着原来的路径返回。

---

# 中间件像一层层包裹

假设中间件顺序是：

```text
Trace → Auth → Timeout → Handler
```

执行过程大致是：

```text
Trace 开始
  Auth 开始
    Timeout 开始
      Handler 执行
    Timeout 结束
  Auth 结束
Trace 结束
```

所以中间件不是一个简单列表。

它更像一层层包裹业务处理器。

越靠外的中间件：

- 越早看到请求
- 越晚看到响应
- 能覆盖越完整的执行过程

理解这一点以后，才能正确安排顺序。

---

# 中间件顺序会改变行为

假设 Trace 放在认证之后。

认证失败的请求可能没有完整 Trace。

如果指标统计放在限流之后，被限流的请求可能没有进入请求总量。

如果异常恢复放得太里面，外层中间件的 Panic 可能无法捕获。

因此中间件顺序需要根据希望观察和保护的范围决定。

一种常见思路是：

```text
异常恢复
  ↓
Trace 和请求标识
  ↓
指标与日志
  ↓
限流
  ↓
认证与权限
  ↓
超时控制
  ↓
业务处理
```

这不是所有系统唯一正确的顺序。

关键是每一层为什么在这里必须说得清楚。

---

# Trace 应该尽量覆盖完整请求

Trace ID 通常需要在请求刚进入系统时读取或创建。

然后向下游继续传递。

这样才能把下面的调用关联起来：

```text
网关
  ↓
订单服务
  ↓
库存服务
  ↓
数据库
```

如果中间某一层忘记传递上下文，后面的 Span 就会变成一条新的链路。

因此上下文传播是中间件设计的重要职责。

但业务 ID 仍然应该单独记录。

Trace 可能被采样，订单号和消息 ID 才能帮助定位具体业务。

---

# 超时中间件不能让工作自动停止

超时中间件可以在规定时间后向调用方返回错误。

但返回超时不代表内部工作一定停止。

如果业务代码、数据库驱动或下游调用没有响应取消信号，它们可能仍然继续执行。

于是出现：

```text
调用方看到超时
  ↓
调用方发起重试
  ↓
上一次请求仍在执行
```

所以超时控制需要和下面的能力配合：

- Context 取消传播
- 数据库查询超时
- 下游调用超时
- 幂等
- 并发控制

中间件只能发出取消信号。

不能保证所有代码都会正确响应。

---

# 认证和权限不是同一件事

认证回答：

> 你是谁？

权限回答：

> 你能不能执行这个操作？

认证通常适合放在公共中间件中，解析 Token 并写入身份上下文。

但具体业务权限可能依赖：

- 订单属于谁
- 当前用户是不是店铺管理员
- 资源当前处于什么状态

这部分不一定适合全部塞进通用中间件。

中间件可以提供身份和通用策略。

领域逻辑仍然需要保护和业务资源相关的权限规则。

---

# 不要把业务逻辑放进通用中间件

假设一个中间件开始处理：

- 创建订单幂等记录
- 检查库存
- 修改用户积分
- 决定订单能否退款

这些行为只属于少数接口，却被放进所有请求共用的执行链。

结果会变成：

- 中间件顺序难以调整
- 业务规则隐藏在入口之外
- 定时任务和 MQ 消费者无法复用
- 测试需要启动完整链路

通用中间件适合处理与传输和治理相关的横切能力。

业务规则应该留在应用或领域层。

---

# 错误转换应该保留语义

基础设施可能返回很多具体错误：

- 数据库唯一键冲突
- 连接超时
- 下游不可用
- 消息发送失败

对外接口不应该直接暴露驱动错误和内部堆栈。

但也不能把所有错误都转换成同一个“系统错误”。

错误转换需要保留调用方真正需要的语义：

- 是否是业务拒绝
- 是否可以重试
- 是否需要重新认证
- 是否属于资源冲突

同时，预期内的业务分支不应该随意作为系统 Error 穿过整条 Trace。

否则错误率和告警会失去意义。

---

# 公共中间件的故障半径很大

一个业务函数出错，通常只影响一个接口。

一个公共中间件出错，可能影响所有接口。

例如：

- Trace 上报阻塞请求
- 日志序列化发生 Panic
- 鉴权缓存不可用导致全部拒绝
- 限流配置错误导致正常请求被拦截

因此公共中间件需要更加保守：

- 明确超时
- 合理降级
- 避免无限阻塞
- 控制资源使用
- 提供独立开关
- 充分测试异常路径

复用越广的组件，变更风险越大。

---

# 默认配置也是架构决定

中间件通常拥有很多配置：

- 超时时间
- 采样率
- 限流阈值
- 是否记录请求体
- 哪些路径跳过认证

如果默认值不安全，每个服务都可能复制错误配置。

例如默认记录完整请求体，可能把密码和 Token 写入日志。

默认没有超时，可能让下游请求无限等待。

所以公共组件应该提供保守且可解释的默认值。

特殊服务可以覆盖，但需要明确知道自己改变了什么。

---

# HTTP 之外的入口也要治理

很多系统只给 HTTP 接口配置中间件。

但业务还可能从下面的入口执行：

- MQ 消费者
- 定时任务
- 命令行任务
- 内部 RPC

这些入口同样需要：

- Trace
- 超时
- 恢复
- 指标
- 身份或任务上下文

如果治理能力只能依赖 HTTP 中间件，其他入口就会变成观察盲区。

可以复用底层能力，但不同入口应该拥有适合自己的执行链。

---

# 小结

架构设计不是多创建几层目录。

它需要控制：

- 依赖方向
- 业务边界
- 技术细节的影响范围
- 公共能力的故障半径

中间件则把 Trace、认证、限流、超时等横切能力放进统一执行链。

设计中间件时需要关注：

- 执行顺序
- 上下文传播
- 错误语义
- 取消是否真正生效
- 是否错误地混入业务规则
- 公共组件失败时影响多大

好的架构不会让系统看起来最复杂。

它真正带来的效果是：

> **业务变化时只修改应该修改的地方，基础设施故障时不会轻易拖垮整个系统。**
