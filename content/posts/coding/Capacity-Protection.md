# 为什么系统不能把所有请求都接进来：限流、熔断和降级

系统流量增长时，一个常见目标是：

> **尽量处理所有请求。**

这个目标在流量正常时没有问题。

但当请求超过系统处理能力以后，继续接收所有请求不一定能让更多用户成功。

反而可能让：

- CPU 被占满
- 数据库连接耗尽
- 请求大量排队
- 所有接口一起超时

最后原本可以成功的一部分请求也全部失败。

所以真实系统还需要一种能力：

> **在资源有限时，主动控制进入系统的工作量。**

---

# 每个系统都有容量上限

一次请求可能消耗：

- CPU
- 内存
- 工作线程
- 数据库连接
- 下游接口配额
- 网络带宽

这些资源都有上限。

假设服务稳定情况下每秒可以处理 1000 个请求。

当流量增加到 1100 时，系统可能只是稍微变慢。

当流量增加到 5000 时，系统不会自动拥有五倍能力。

多出来的请求只能：

- 排队
- 超时
- 被拒绝

容量保护决定这些请求在哪里等待，以及什么时候停止等待。

---

# 排队不能创造处理能力

增加队列以后，请求可以暂时等待。

这有助于吸收短时间的流量波动。

但如果请求进入速度长期大于处理速度，队列会越来越长。

例如：

```text
每秒进入 1200 个请求
每秒只能处理 1000 个请求
```

每秒会积压 200 个请求。

一分钟以后就是 12000 个。

等待时间不断增加，直到大量请求在队列里超时。

所以队列只能平滑短暂峰值。

它不能解决长期容量不足。

---

# 为什么过载会突然恶化

系统接近容量上限以后，性能通常不是线性下降。

请求变慢会占用资源更久。

资源被占用更久，又会让后续请求等待更久。

例如数据库查询从 50 毫秒变成 2 秒以后，同样数量的连接能完成的请求会大幅减少。

调用方看到超时，还可能自动重试。

于是系统进入循环：

```text
请求变慢
  ↓
资源占用时间变长
  ↓
更多请求排队和超时
  ↓
产生更多重试
  ↓
系统继续变慢
```

这也是为什么过载常常看起来是突然发生的。

---

# 限流是在入口控制流量

限流规定单位时间内允许多少请求进入。

例如：

```text
每个用户每秒最多 10 次
整个接口每秒最多 1000 次
```

超过限制的请求可以：

- 立即拒绝
- 稍后重试
- 进入有界队列

立即拒绝听起来不友好。

但相比让请求等待几十秒以后全部超时，快速返回通常更容易恢复。

调用方也能明确知道当前系统繁忙。

---

# 限流应该按什么维度

只设置一个全局请求数不一定够。

不同接口的成本可能完全不同。

例如：

- 查询缓存只需要 2 毫秒
- 导出报表需要几十秒
- 上传文件占用大量带宽

一次报表请求和一次缓存查询不能简单认为成本相同。

限流可以考虑：

- 用户
- 租户
- 接口
- 服务实例
- 整个集群
- 下游资源

还要防止一个大客户占满所有资源，影响其他用户。

这时可以为不同租户保留独立配额或并发上限。

---

# 并发限制和请求速率不同

每秒 1000 个请求，不代表系统同时只有 1000 个请求。

如果每个请求执行 10 秒，系统里可能同时存在大量进行中的工作。

因此除了请求速率，还需要关注并发数。

例如：

- 同时最多执行 20 个导出任务
- 同时最多使用 50 个数据库连接
- 同时最多调用第三方支付 100 次

并发限制保护的是正在被占用的资源。

速率限制控制的是一段时间内进入多少请求。

它们解决的问题并不相同。

---

# 背压让上游知道下游已经很忙

假设消息生产速度一直快于消费速度。

如果生产方完全不关心积压，队列可能越来越大。

最终出现：

- 消息延迟很高
- 磁盘空间不足
- 任务过期后仍在执行
- 故障恢复需要很长时间

背压的意思是：

> **下游处理不过来时，把压力传回上游。**

上游可以选择：

- 降低生产速度
- 暂停非关键任务
- 合并重复任务
- 拒绝新的低优先级请求

如果压力只能不断向下游堆积，系统只是推迟故障发生。

---

# 超时是一种资源边界

调用下游时，如果没有超时，请求可能无限等待。

连接、线程和内存也会一直被占用。

设置超时表示：

> **这项工作超过多久以后，对当前请求已经没有价值。**

但超时时间不能每一层都设置成相同数值。

假设入口总预算只有 2 秒。

内部调用三个下游，每个都等待 2 秒，整个请求可能远远超过入口预算。

更合理的是把剩余时间继续向下传递。

每一层都知道当前还剩多少时间。

---

# 重试也要消耗容量

当系统开始失败时，重试会增加额外流量。

如果每个请求最多重试三次，最坏情况下流量可能被放大数倍。

因此重试需要限制：

- 只重试可能恢复的错误
- 使用指数退避
- 增加随机抖动
- 设置最大次数
- 遵守整体时间预算

系统还可以设置重试预算。

例如只允许重试流量占正常流量的一小部分。

这样下游故障时，不会让重试完全占满服务容量。

---

# 熔断是在失败时暂时停止调用

假设支付服务已经不可用。

订单服务仍然不断调用它，每次等待超时以后再返回失败。

这些调用不会成功，却一直占用资源。

熔断器会观察一段时间内的失败情况。

失败超过阈值以后，暂时停止真实调用，直接快速失败。

过一段时间再允许少量请求探测恢复情况。

熔断的目的不是修复下游。

而是：

> **在下游明显不可用时，停止继续浪费本服务的资源。**

---

# 熔断不能只看所有错误

参数错误、余额不足和权限不足属于正常业务结果。

它们不代表下游服务故障。

如果把所有非成功响应都计入熔断，正常业务拒绝也可能触发熔断。

因此错误分类非常重要。

熔断通常应该关注：

- 连接失败
- 超时
- 服务内部错误
- 明显的系统不可用

预期内的业务错误不应该污染系统故障指标。

---

# 降级是先保住核心能力

一个接口可能依赖很多附加能力。

例如商品详情页需要：

- 商品基本信息
- 实时推荐
- 用户评价
- 营销活动
- 浏览记录

如果推荐服务失败，整个商品详情都返回失败，故障范围就被放大了。

可以在下游不可用时降级：

- 不展示个性化推荐
- 返回默认推荐
- 使用短时间旧缓存
- 暂停非核心统计

降级需要提前区分：

> **哪些是核心结果，哪些是可以暂时缺失的附加能力。**

---

# 降级不能破坏业务正确性

不是所有功能都可以返回旧数据或默认值。

例如：

- 账户余额
- 支付结果
- 权限判断
- 实际库存

如果无法确认正确状态，快速失败可能比返回错误数据更安全。

所以降级不是“出错就随便返回一个值”。

它必须明确：

- 用户会看到什么
- 数据允许多旧
- 是否影响资金和权限
- 恢复以后怎样校正

性能和可用性不能以业务正确性为代价。

---

# 隔离避免一个功能占满所有资源

假设普通查询和报表导出共用同一个工作池。

大量报表任务可能占满所有线程和数据库连接。

结果连最简单的订单查询也无法执行。

可以为不同工作负载设置独立资源：

- 独立线程池
- 独立连接池
- 独立队列
- 独立实例

这种思路通常叫做舱壁隔离。

它的目标是：

> **一个功能过载时，不要耗尽整个系统的共同资源。**

---

# 自动扩容不是立即发生的

自动扩容可以增加处理能力。

但它需要时间：

- 监控发现负载升高
- 触发扩容策略
- 创建新实例
- 启动程序
- 完成健康检查
- 开始接收流量

突发流量可能在新实例准备好之前就已经压垮系统。

而且如果瓶颈在数据库，增加应用实例还会创建更多连接，让数据库压力更大。

所以扩容不能代替限流、背压和降级。

它们解决的是不同时间尺度的问题。

---

# 容量需要通过运行数据验证

系统能处理多少流量，不能只靠配置推算。

需要观察和测试：

- 吞吐量
- P95、P99 延迟
- 错误率
- 活跃请求数
- 队列长度
- 数据库连接等待
- CPU、内存和 IO
- 下游调用延迟

压测时不应该只找最高 QPS。

还要找到：

- 从哪里开始明显变慢
- 哪个资源最先饱和
- 过载以后能否快速恢复
- 限流和降级是否按预期生效

容量规划真正关心的是稳定运行区间。

不是系统崩溃前一瞬间的最高数字。

---

# Kratos 把治理能力放在 Middleware

Kratos 提供服务端限流和客户端熔断 Middleware。

两者所在方向不同：

```text
调用方
  ↓ 客户端熔断：下游明显故障时停止浪费调用
服务端
  ↓ 服务端限流：超过本服务容量时拒绝部分请求
业务处理
```

服务端限流可以在 Server 构造时统一注册：

```go
import (
	"github.com/go-kratos/kratos/contrib/otel/v3/tracing"
	"github.com/go-kratos/kratos/v3/middleware/ratelimit"
	"github.com/go-kratos/kratos/v3/middleware/recovery"
	"github.com/go-kratos/kratos/v3/transport/http"
)

srv := http.NewServer(
	http.Address(":8000"),
	http.Middleware(
		tracing.Server(),
		recovery.Recovery(),
		ratelimit.Server(),
	),
)
```

这里把 Trace 放在 Recovery 外层，让业务 Panic 被恢复成 Error 后，Trace 仍然能够记录失败状态。

限流发生在业务处理之前，可以避免请求已经占用大量数据库和下游资源以后才失败。

但框架默认能力只是起点。

按用户、租户、接口成本设置配额时，仍然需要结合业务身份和自己的 Limiter 实现。

---

# 熔断应该配置在 Client 侧

调用支付服务的 Kratos gRPC Client 可以加入熔断 Middleware：

```go
import (
	"context"
	"time"

	paymentv1 "example/api/payment/v1"

	"github.com/go-kratos/kratos/contrib/otel/v3/tracing"
	"github.com/go-kratos/kratos/v3/middleware/circuitbreaker"
	"github.com/go-kratos/kratos/v3/registry"
	"github.com/go-kratos/kratos/v3/transport/grpc"
)

func NewPaymentClient(discovery registry.Discovery) (paymentv1.PaymentServiceClient, error) {
	conn, err := grpc.NewClient(
		context.Background(),
		grpc.WithEndpoint("discovery:///payment"),
		grpc.WithDiscovery(discovery),
		grpc.WithTimeout(800*time.Millisecond),
		grpc.WithMiddleware(
			tracing.Client(),
			circuitbreaker.Client(),
		),
	)
	if err != nil {
		return nil, err
	}
	return paymentv1.NewPaymentServiceClient(conn), nil
}
```

这里的 `context.Background()` 用于应用启动时创建长期 Client。

它不是某一次支付请求的业务 Context。

真正调用支付接口时，Repo 必须继续传递从 Biz 收到的 `ctx`：

```go
func (r *paymentRepo) Pay(
	ctx context.Context,
	orderID int64,
	amount int64,
) error {
	_, err := r.client.Pay(ctx, &paymentv1.PayRequest{
		OrderId: orderID,
		Amount:  amount,
	})
	if err != nil {
		return mapPaymentError(err)
	}
	return nil
}
```

这样 `tracing.Client()` 才能创建当前请求的子 Span，并把 Trace Carrier 注入下游请求。

上游的 Deadline 和 Cancellation 也会沿着这个 Context 传给支付服务。

如果在 `Pay` 里换成新的 `context.Background()`，Client Middleware 虽然仍然会创建 Span，但它已经属于另一条链路，也不会随着原请求超时而取消。

熔断器看到的是客户端调用结果。

因此业务错误必须拥有正确的 Kratos Error Code。

余额不足如果被错误包装成 500，熔断器可能把正常业务拒绝当成支付服务故障。

错误分类、Trace 和治理策略不是互相独立的功能。

它们通过同一条 Middleware 链协作。

---

# 降级仍然属于业务用例

Kratos Middleware 可以发现错误、执行限流和熔断。

但它不知道“商品推荐失败时能不能返回默认推荐”。

这个决定应该留在 Biz：

```go
func (uc *ProductUsecase) Detail(
	ctx context.Context,
	id int64,
) (*ProductDetail, error) {
	product, err := uc.repo.FindByID(ctx, id)
	if err != nil {
		return nil, err
	}

	recommendations, err := uc.recommend.List(ctx, id)
	if err != nil {
		// 推荐是非核心能力，可以降级为空列表。
		recommendations = nil
	}
	return &ProductDetail{
		Product:         product,
		Recommendations: recommendations,
	}, nil
}
```

账户余额、权限、支付结果这类核心数据失败时，则不应该使用相同降级方式。

降级也不等于静默吞掉错误。

实际项目仍然需要记录降级指标或 Trace Event，否则推荐服务长期故障也可能没有人发现。

框架提供治理机制。

业务层决定什么可以牺牲。

这正符合 Kratos 的工具箱哲学：

> **公共机制由 Middleware 统一实现，业务取舍由 Biz 明确表达。**

> 示例使用 Kratos v3。v3 的默认 Circuit Breaker 不再隐式依赖 Aegis；自定义实现应通过明确的工厂或组件注入。

---

# 小结

系统不能处理无限请求。

当流量超过容量以后，继续接收所有工作只会增加排队和超时。

容量保护需要组合使用：

- 限流控制进入速度
- 并发限制保护稀缺资源
- 背压把压力传回上游
- 超时限制无价值的等待
- 熔断停止调用明显故障的下游
- 降级优先保住核心能力
- 隔离控制故障范围

这些机制看起来是在拒绝请求。

但它们真正保护的是：

> **让系统在压力下仍然有一部分请求能够快速、正确地完成。**

工程系统追求的不是任何时候都接受所有流量。

而是知道自己的能力边界，并在超过边界时以可预测的方式失败和恢复。
